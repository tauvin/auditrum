# What's new in 1.0

> **Draft.** 1.0 is not cut yet — this is the cumulative summary of
> everything that has landed since 0.3.1, which 1.0 will ship as a stable,
> supported surface. It becomes the 1.0 release notes when the version is
> tagged. For the exact per-release detail, see the [Changelog](changelog.md);
> for upgrade mechanics, the migration guide (0.7).

1.0 is **not a feature release** — it is the moment the surface built
across 0.3–0.6 becomes a stable public commitment (see
[API stability](api-stability.md)). Here is the whole picture.

## The shape of auditrum 1.0

* **PostgreSQL-trigger-as-source-of-truth.** Every tracked write is
  recorded by a database trigger, not application code — so even a
  compromised or bypassed app cannot skip or forge the audit trail.
* **Framework-agnostic core, Django-first integration.** A small core
  (`auditrum.tracking`, `auditrum.executor`, `auditrum.schema`) with a
  rich Django integration on top; SQLAlchemy is supported but
  experimental.
* **One audit-log table, partitioned by month**, with per-request
  context (user, IP, URL, request id, source) attached to every event.

## Major capabilities

### Audit logging & rich context (0.3.0)
The framework-agnostic core, the `ConnectionExecutor` protocol, and the
`audit_context` table that attaches per-request metadata to every event
via a PL/pgSQL helper.

### Time travel (0.3.0–0.5)
Reconstruct any row's state at any past timestamp
(`reconstruct_row` / `reconstruct_field_history`), or a whole table as of
a timestamp (`reconstruct_table`, with a `stream=True` server-side-cursor
mode for large logs). Measured at ~5–11 ms even on the deepest real
histories (570–2,207 revisions); see [Performance](performance.md).

### Tamper evidence — the hash chain (0.3.0–0.5)
An optional SHA-256 chain over the audit log: each row hashes its content
plus the previous row's hash, so any post-hoc edit, deletion, or
insertion breaks the chain and is detected by `verify_chain`. Canonical
JSON payloads, a monotonic `chain_seq` assigned under an advisory lock,
and external **tip anchoring** (`get_chain_tip`) to detect tail-row
deletion. First-class to enable and operate on Django in 0.5
(`PGAUDIT_HASH_CHAIN`, `auditrum_enable_hash_chain`,
`auditrum_verify_chain`).

### Security & hardening (0.3.1)
`SECURITY DEFINER` trigger functions, an append-only model (`auditrum
harden` revokes `INSERT`/`UPDATE`/`DELETE` on the audit tables from the
app role), the documented two-role deployment split, GUC names bound as
parameters in the runtime injection, and a fixed SQL-injection vector in
`set_var` (0.3.2).

### Retention & operations
Calendar-aware retention (`auditrum purge`, partition-aware drops),
monthly partition provisioning (`audit_add_partitions`), a schema-refresh
escape hatch (`auditrum_refresh_schema`), and observability hooks
(Prometheus collector + Grafana dashboard).

### API stabilization (0.3.2 / 0.4)
The public/private boundary drawn explicitly: `__all__` locked on every
module, a strict `pyrefly` typing gate in CI, property-based tests, a coverage
floor, remediation-oriented error messages, and the
[API stability](api-stability.md) classification that 1.0's promise rests on.

### Diff format & developer experience (0.4)
The paired `{field: {old, new}}` diff shape for every operation; a real
`old → new` admin History view; Celery/RQ task-context helpers;
async-aware `@with_context` / `@with_change_reason` / `@audit_task`;
and `update_current_context()` for django-ninja / DRF late authentication
(0.4.5).

### Performance, validated (0.5)
Real numbers from **two production deployments** (catalog, bidwise) in
[Performance](performance.md) and the [case studies](case-studies/catalog.md):
trigger overhead ~0.3–1.4 ms/write (scales with row width), time-travel
sub-linear in history depth, and the finding that drove making the
GIN-on-diff index opt-in.

### Documentation (0.6)
A full docs site on GitHub Pages: an autogenerated
[API reference](reference/api.md), a [production deployment guide](deployment.md),
a [migration cookbook](migration-cookbook.md), [performance tuning](performance-tuning.md),
the two [case studies](case-studies/catalog.md), and a 5-minute
[Quickstart](quickstart.md).

## Breaking changes since 0.3.x

These are why this is `1.0` rather than a `0.3.x` patch line. The
companion migration guide (0.7) covers each in detail.

* **`content_type_id` column + `AuditLog.content_type` GenericForeignKey
  removed** (0.4.0) — identity is keyed on `table_name`; a migration drops
  the column.
* **`auditlog.diff` is now the paired `{field: {old, new}}` shape** for
  every operation (0.4.1), replacing the old `{field: new_value}` form;
  `jsonb_strip_nulls` removed so NULL-target updates are no longer dropped.
  A back-fill script for existing rows is in the changelog.
* **`_validate_ident` alias removed** (0.3.2) — use
  `auditrum.tracking.spec.validate_identifier`.
* **The `diff` GIN index is opt-in (default off)** (0.5) — migration `0004`
  drops it; set `PGAUDIT_DIFF_GIN_INDEX=True` to keep it.

## The 1.0 promise

Everything in each module's `__all__` is stable for the entire 1.x
series; breaking changes wait for 2.0 behind a deprecation period. LTS
bug-fix backports for at least 12 months. See [API stability](api-stability.md)
for the full contract.
